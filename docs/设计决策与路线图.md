# NexMesh 设计决策与路线图

> NexMesh 是从零开始构建的企业级 .NET 10 应用框架:显式优于约定、每包独立可用、默认零基础设施、AI 友好。
> 本文档记录已定的关键技术决策与演进路线。

---

## 一、技术基座:FastEndpoints 还是 Minimal API?

**结论:框架核心与 API 风格解耦;官方脚手架与参考实现默认 FastEndpoints。**

| 层 | 基座 | 说明 |
|---|---|---|
| `NexMesh.Core` 及数据/缓存/事件/可观测等包 | **原生 ASP.NET Core 抽象** | 不绑定任何 API 风格:Minimal API、MVC、FastEndpoints 服务均可使用 |
| 服务端点层(模板/参考服务/规范) | **FastEndpoints(v8)** | 显式端点类 `Endpoint<TReq, TResp>`(REPR 模式) |

**为什么默认 FastEndpoints 而不是裸 Minimal API:**

1. **结构化**:一个端点一个类(Request/Endpoint/Response 同文件),大项目不散架;裸 Minimal API 缺乏组织范式,端点一多就乱
2. **性能**:接近 Minimal API(共享同一条路由管道),明显优于 MVC 控制器
3. **开箱能力**:内置 FluentValidation 接线、前置/后置处理器(替代自建管道)
4. **AI 友好**:端点即类型,生成/审查的边界清晰

**如果偏好 Minimal API:** NexMesh 的中间件(异常/TraceId)、健康检查、限流、数据层、缓存、事件全部照常可用,只有端点写法自选——规范 01 的分层约定同样适用(把 endpoint 类换成同目录的 route group 即可)。

## 二、已定决策

| 决策 | 结论 | 理由 |
|---|---|---|
| API 路线 | **FastEndpoints 显式端点 + Refit 客户端** | 见上节;不做"接口→自动生成端点"的编译期魔法 |
| ORM | **FreeSql 锚定**,接口层 ORM 无关设计 | 团队习惯 + 文档规范可平移;`AddNexMeshDb` 是唯一入口,FreeSql 类型不出契约 |
| 数据库迁移 | **SQL 脚本是生产唯一权威**(NexMesh.Data.Migrations);`UseAutoSyncStructure` 仅开发期 | CodeFirst 自动同步处理不了部分唯一索引/列改名/默认值回填 |
| 对象映射 | Mapster(`IMapper` DI + 集中配置) | 零配置 + 集中规则 |
| 目标框架 | **仅 net10.0** | 不背多版本包袱 |
| 分页字段 | `Items/TotalCount/PageIndex/PageSize/TotalPages` | 通用命名,契约稳定 |
| 服务注册 | 标记接口 + `AddNexMeshServices(assembly)` 一行显式扫描 | 便利与显式兼得:那行注册看得见 |
| 可观测 | Serilog + OpenTelemetry,OTLP 统一导出 | 不直连厂商 Agent,Collector 中转 |
| 事件 | 统一 `INexMeshEventPublisher`:Memory(进程内)/ RabbitMQ(CAP Outbox) | 零基础设施默认 + 生产可靠升级同契约 |
| 缓存 | Redis(FreeRedis)与内存同契约,自动降级 | 本地/测试零依赖 |

## 三、路线图

### 已完成

| 版本 | 内容 |
|---|---|
| v0.1.0 | 仓库基线(CPM/CI/模板)、Core(ApiResult/异常/健康检查)、参考服务 |
| v0.2.0 | 十包全量:数据/缓存/认证/事件/可观测/弹性/映射/工具 + 部署指南;45 测试 |
| v0.3.0 | SQL 迁移运行器、InsertOrUpdate、标记接口注册、17 篇开发规范;50 测试 |

### 规划中(按存量服务迁移阻塞排序)

| 优先级 | 事项 | 说明 |
|---|---|---|
| P0 | `NexMesh.Auth.OpenIdConnect` | 对接 OIDC 单点登录(JWT 颁发在 IdP) |
| P0 | `NexMesh.Discovery.Nacos` | 服务注册/发现/配置中心 |
| P1 | 契约驱动的客户端生成器 | `IHttpClientApi` → Refit 注册(只做客户端侧,不做端点魔法) |
| P1 | 存量服务迁移试点 | 选一个中型服务平移到 NexMesh,沉淀迁移手册 |
| P2 | 发布内部 NuGet 源 + 文档站 | nupkg 已就绪,等内部源地址 |

### 原则红线(任何迭代不破)

1. 不做模块管道/约定激活的隐式魔法
2. 每个包独立可用,禁止包间横向依赖
3. 第三方类型不出公共契约
4. 未配置外部依赖时服务必须可启动、测试可运行
