# 16 数据库迁移规范

> 立场来自生产实战教训:CodeFirst 自动同步在生产不可靠;散落的手写 SQL 没有统一运行机制、无法审计。
> NexMesh 的立场:**SQL 脚本是生产迁移的唯一权威,AutoSyncStructure 只用于开发期白板起步。**

## 运行器(NexMesh.Data.Migrations)

```csharp
builder.Services.AddNexMeshMigrations();          // 默认:Scripts/ 目录 + 入口程序集嵌入 *.sql
var app = builder.Build();
app.ApplyNexMeshMigrations();                     // 启动时执行未应用脚本(幂等,可安全重复启动)
```

## 脚本约定

- **[强制]** 命名 `V{序号:三位}__{描述}.sql`(如 `V001__create_region.sql`);文件名即执行序,**禁止插入已有序号之间**(改用下一个序号)
- **[强制]** 已发布(已在任何环境执行过)的脚本**永远不可修改**——写错了?新写一个修复脚本
- **[强制]** 一个脚本一个主题,可独立回看;跨库 DDL 不进脚本(各服务管各库)
- **[强制]** 破坏性操作(删列/删表)两段式:先发"停用"脚本(代码不再读写),下个版本再发"删除"脚本

## AutoSyncStructure 边界

| 场景 | 用法 |
|---|---|
| 开发起步(新库/原型) | `UseAutoSyncStructure=true` 允许 |
| 测试/生产 | **[强制] false**,结构变更走脚本 |

AutoSyncStructure 处理不了、必须手写脚本的典型生产场景:

```sql
-- 软删除与唯一索引共存:部分唯一索引(WHERE 排除已删除行)
CREATE UNIQUE INDEX ux_region_code ON region(code) WHERE isdeleted = false;
```

```sql
-- 列改名/类型收窄/默认值回填,CodeFirst 都不可靠,一律脚本
ALTER TABLE region ADD COLUMN code_new TEXT;
UPDATE region SET code_new = code;
ALTER TABLE region DROP COLUMN code;
ALTER TABLE region RENAME COLUMN code_new TO code;
```

## 多实例与发布

- **[强制]** 多实例部署时迁移只跑一处:K8s 用 initContainer / Job 执行,或首实例锁(版本表主键天然幂等,并发至多重复报错一次)
- **[建议]** 脚本随代码 PR 提交评审,与业务变更同批发布;执行日志(Information 级)保留审计轨迹

## 版本表

`__nexmesh_migrations(script, applied_at)`——每脚本一行;排查环境差异先 diff 各环境版本表。

## 方言边界(当前版本)

- 版本表 `CREATE TABLE IF NOT EXISTS` 与"脚本+记录同事务"已在 **PostgreSQL/SQLite** 验证;**SQL Server** 不支持该建表语法、**MySQL** DDL 隐式提交使事务原子性失效——这两类库使用迁移器前需自行验证并调整版本表建表语句
