# 大型项目指南

> 适用场景:接口越来越多、多人协作、多个数据库、多个租户(院区/门店/分公司)独立部署。
> 这篇指南按"项目长大的顺序"组织——每个阶段遇到什么信号、做什么改造。

## 判断信号:什么时候需要这篇

| 信号 | 说明 |
|---|---|
| 接口超过 50 个 | 单文件/单目录已经翻不动了 |
| 2 人以上同时改代码 | 合并冲突频发,职责边界模糊 |
| 要接第二个数据库 | 报表库/历史库与业务库分离 |
| 多个租户独立部署 | 每套部署的配置、数据、开关不同 |
| 要上 AI 能力 | 审批、提示词、开关需要统一管理 |

命中两条以上,就按下面的顺序改造。

---

## 1. 解决方案分层:从 1 个项目变成 4 个

小项目一个工程就够(见[快速开始](快速开始.md))。长大后的标准结构:

```
MyApp.slnx
├── src/
│   ├── MyApp.Contracts/      # 接口契约层:全部 IServiceApi 接口 + DTO
│   ├── MyApp.Repository/     # 数据层:实体 + 仓储(IFreeSql 访问)
│   ├── MyApp.Core/           # 业务层:契约的实现类、业务逻辑
│   └── MyApp.WebServer/      # 宿主:Program.cs、配置、启动
├── tests/
│   └── MyApp.Core.Tests/     # 业务测试(随业务一起写)
└── docs/
```

**依赖方向只有一条**(谁也不许反向引用):

```
WebServer → Core → Repository → Contracts
```

**各层放什么**:

| 工程 | 放什么 | 不放什么 |
|---|---|---|
| Contracts | 接口、请求/响应 DTO | 任何逻辑 |
| Repository | 实体类、仓储类(拼查询) | 业务判断 |
| Core | 接口实现、领域逻辑、模块初始化 | 数据库连接细节 |
| WebServer | Program.cs、appsettings、日志配置 | 业务代码 |

**为什么这样分**:前端同事只要拿 Contracts 就能对接;新同事从 Core 的一个域目录读懂一个业务;换 Web 宿主(比如加 gRPC)不动业务。

## 2. 按业务域组织目录

不要按技术分层放文件(所有 Service 一堆、所有 Dto 一堆),**按业务域**:

```
MyApp.Contracts/
├── Orders/                  # 订单域
│   ├── IOrderApi.cs
│   └── DTOs/Request/...  DTOs/Response/...
├── Payment/                 # 支付域
│   ├── IPaymentApi.cs
│   └── DTOs/...
└── Identity/                # 用户权限域
    └── IAuthApi.cs
MyApp.Core/
├── Orders/                  # 与 Contracts 一一对应
│   └── OrderService.cs
├── Payment/
└── Identity/
```

规则:**一个域一个目录,Contracts 和 Core 目录名完全一致**。找"支付相关的代码"就是进两个 Payment 目录。

## 3. 装配:从简装换到模块宿主

小项目用 `AddNexMeshService()` 一行装完。大项目换成**模块宿主**,获得分阶段初始化和认证装配位:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.AddNexMeshHost(x =>
{
    x.AddSecurity(security =>
    {
        security.AddCurrentUser<AppUserInfo>();   // 强类型当前用户
    });
    // x.AddDBSource<ReportDBSource>();           // 第二个数据库在这里挂
});

var app = builder.Build();
app.UseNexMeshHost();                             // 管线顺序框架负责
```

**模块初始化**(建表、种子数据、领域注册)放在 Core 层的模块类里,由宿主自动发现执行——WebServer 的 Program.cs 永远保持干净。

## 4. 配置管理:三份配置各管一摊

```
WebServer/
├── Config/
│   ├── MyApp.json            # 主配置:进 git,团队共享
│   └── MyApp.local.json      # 本地覆盖:不进 git(.gitignore),每人自己一份
└── appsettings.json          # 框架级默认:进 git
```

主配置放业务开关、模型选择这类"团队约定";**local 覆盖放个人环境差异**——数据库地址、测试用的 AI Key。加载顺序:主配置 → local 覆盖(同名键生效的是后者)。

```csharp
builder.Configuration
    .AddJsonFile("Config/MyApp.json", optional: false, reloadOnChange: true)
    .AddJsonFile("Config/MyApp.local.json", optional: true, reloadOnChange: true);
```

> ⚠️ `.gitignore` 里加 `*.local.json`——密钥永远不进仓库。

## 5. 多数据源

主库之外再挂库(报表库/历史库):

```csharp
builder.AddNexMeshHost(x =>
{
    x.AddDBSource<ReportDBSource>();   // 类型化第二库
});
```

要点:

- 每个库一个 `DBSource` 类,业务按类型注入,不会拿错库;
- 实体跟着库走:报表实体放 ReportDBSource 对应的目录,注释里写清归属;
- 跨库没有分布式事务——需要一致性的数据放同一个库。

## 6. 用户与权限(RBAC)

框架提供登录与令牌(见[快速开始](快速开始.md)第 5 步),权限体系按这个思路搭:

1. **强类型当前用户**:装配时 `AddCurrentUser<AppUserInfo>()`,业务里注入 `ICurrentUser<AppUserInfo>` 直接拿姓名/角色/部门;
2. **权限码**:约定形如 `order:refund:approve` 的权限码字符串,存库、挂角色;
3. **接口侧**:契约方法标 `[Authorize]`(要求登录),细粒度权限在服务内校验(注入当前用户判权限码);
4. **菜单/按钮权限**:前端按登录接口返回的权限码渲染——后端只认权限码,不关心前端长什么样。

## 7. AI 能力的规模化组织

大项目里 AI 场景会快速膨胀,三条纪律:

**① 高危必审批**:凡 AI 触发的写操作,工具标 `NexMeshRiskLevel.High`,装配审批门(见[包实战案例](包实战案例.md)第 5 节)。上线前给审批端点配角色门槛。

**② 提示词当资产管理**:不要把提示词写在 C# 字符串里。用文件目录管理:

```
WebServer/Prompts/
└── order.risk-review/       # 一个场景一个目录
    ├── system.md            # 角色与输出约定
    └── user.md              # 任务模板,{{payload}} 占位
```

提示词改动走代码评审(git diff 可见),头部注释标版本号——排查"某天起 AI 输出变差"全靠它。

**③ 功能开关两级**:全局总闸 + 场景开关。不同租户对 AI 的接受度不同,部署时改配置即可关停,不用改代码。

## 8. 事件解耦

"一个动作完成后要触发好几件事"(下单成功 → 发通知 + 记统计 + 同步外部系统)时,用事件总线拆开,调用方只管发事件:

```csharp
await publisher.PublishAsync("order:created", new { OrderId = id });
```

```csharp
public class OrderEvents : IEventSubscriber
{
    [EventSubscribe("order:created", NumRetries = 3)]
    public Task OnCreated(EventContext ctx) { /* 通知/统计/同步 */ }
}
```

可靠性语义(有界队列/停机排干/异常隔离)见[框架质量保障](框架质量契约.md)第五节——处理方挂了不影响主流程。

## 9. 定时与后台

报表、清理、轮询放 Worker(见[包实战案例](包实战案例.md)第 11 节),**不要**在 Web 请求里做长任务;需要"审批通过后延时执行"的用工作流(第 6 节)。

## 10. 上线检查清单

上线前逐项打勾:

| # | 检查项 | 怎么做 |
|---|---|---|
| 1 | 数据库自动建表已关闭 | `AutoSyncStructure: false`,表结构变更走脚本评审 |
| 2 | AI Key 不在配置文件 | `${ENV|}` 占位符 + 环境变量/密钥管理 |
| 3 | `*.local.json` 不进 git | 检查 .gitignore 与仓库历史 |
| 4 | 认证会话可共享 | 多实例部署必配 Redis 会话存储 |
| 5 | CORS 白名单 | 不要 `AllowAnyOrigin` + 凭证同时开 |
| 6 | 文档页关闭生产外访问 | Scalar 按环境开关 |
| 7 | 审批端点有权限门槛 | 高危 AI 操作的审批端点要求特定角色 |
| 8 | 登录限流确认开启 | 默认 5 次/分钟,按业务评估调整 |
| 9 | 健康检查接入探针 | `/health` 接入负载均衡/容器探针 |
| 10 | 日志落盘与保留策略 | 按天/级别分文件,配置保留天数 |
| 11 | 事件队列容量评估 | `Capacity` 按峰值调,观察 `queue_depth` 指标 |
| 12 | 数据库连接串加密/托管 | 环境变量或密钥服务 |

## 11. 团队协作约定

- **测试跟着业务工程走**:`tests/MyApp.Core.Tests` 随功能一起提交;核心域(钱、权限、状态机)必须有测试;
- **公共 API 变更要有意识**:给外部/前端用的类型改签名前先想兼容,破坏性变更通知使用方;
- **契约即文档**:接口的 XML 注释会出现在 OpenAPI 文档里,写清楚等于给前端省一次沟通;
- **目录即导航**:新人入职,让他读 Contracts 目录树就能画出系统全貌。

## 12. 常见坑

| 现象 | 原因 | 解决 |
|---|---|---|
| 本地起不来,提示 dll 被占用 | 服务还开着就编译 | 先停服务再编译 |
| 查询查不出已删除记录 | 软删过滤是全局的 | 这是设计行为;确要查已删数据走原生 SQL 通道 |
| 配置改了不生效 | 配置绑定发生在启动时 | 重启;`reloadOnChange` 只对支持热更的配置生效 |
| 两套部署互相看到对方的数据 | 多租户字段没配过滤 | 实体实现租户接口,让全局过滤生效 |
| 事件处理器里拿不到当前用户 | 后台执行没有 HTTP 上下文 | 从 `EventContext.Context` 取发布时刻的快照 |
